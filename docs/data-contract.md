# KMS schema v2 data contract

The embedded payload has `schemaVersion: 2`, `title`, `generatedAt`, `items`, and `relations`.
An item has a unique `id`, `title`, `kind` (`document`, `tool`, or `ai_asset`) and metadata fields. `domain`, department, and tags are metadata, never generated nodes. URLs must be HTTP(S), contain no user information, and are validated before publication.

Only an `ai_asset` whose subtype is exactly `프롬프트` may have a `prompt` field. Legacy CSV prompt columns are intentionally excluded; they never create standalone assets. Use explicit approved `items` input, `--knowledge`, or `knowledge_file` to register a prompt asset.

Relations have unique IDs, existing distinct endpoint `source` and `target` IDs, and a `type` from `references`, `based_on`, `explains`, `uses_with`, or `related`. Legacy tools create `references` edges to their approved referenced documents. Optional strings `label`, `evidence`, and HTTP(S) `evidenceUrl` preserve explanation and source evidence.

Relation direction is `source → target`: a tool `references` a document, an item `based_on` its source material, and an explanatory manual `explains` the rule it describes. Those three types are directed, so a reverse record is a distinct relationship and is accepted. `uses_with` and `related` are symmetric: the UI renders them as undirected context and the validator rejects a reverse duplicate (`A → B` plus `B → A`) of the same type. Use one record per pair, with either endpoint order.

Explicit `ID`/`id` values take precedence. Without one, legacy tools derive a stable ID from their normalized URL and documents from their name. Renaming a legacy document therefore changes its ID; set an explicit ID before renaming to preserve identity.

For legacy reference-data masters, only documents referenced by approved legacy tools are published. Approved explicit independent items do not require a legacy tool reference. Internal reports, unmatched values, and snapshots are stored outside the output directory in `state_dir` (or a sibling hidden state directory).

Approved explicit independent documents/tools/registered AI assets are also supported through optional CSV/Sheets tabs and separate Notion databases. Each explicit row requires `approved/승인`; a missing/false approval never publishes. Optional `prompt/프롬프트` is accepted only for `ai_asset` subtype `프롬프트`, preserving existing registered assets without generation/execution. Existing `--knowledge` JSON is administrator-selected, already-public input and retains its prior approval semantics. No automatic AI generation is added. See [examples](../sample/explicit-inputs/README.md).

Optional item strings are `sourceId`, `sourceUrl` (validated HTTP(S)), `sourceUpdatedAt` (original modification time), and `collectedAt` (collection time). `updatedAt` retains the legacy registration-date mapping. Legacy IDs do not change when optional provenance is supplied. New explicit inputs require `id/ID` or `source_id/출처ID`; only these new rows fall back to `source-<SHA256 first 16 hex chars>`. Notion provides its page ID as source ID, page URL, and `last_edited_time`. Legacy Notion data DB explicit IDs are now preserved; existing blank-ID fallback remains unchanged.

Optional `sharedFolders` and `sharedProjects` arrays contain `{id,title,description}`. Projects may also have `folderId`, which must refer to an approved shared folder; import column is `folder_id/폴더ID`. This retains the folder → project → item hierarchy. Optional item `folderIds`/`projectIds` arrays must refer to these approved groups. They are shared source-managed metadata, distinct from browser-local personal organization. All IDs, endpoints, duplicate relation pairs, memberships and URLs are validated before HTML replacement. Approved references to unpublished endpoints fail the build.

Optional `reviewCandidates` contains `{itemId,changedSourceIds:string[],reason,removedSourceCount?:number}`. Only currently published origin IDs appear in `changedSourceIds`; removed origins expose a count only. A validated private `knowledge-snapshot.json` baseline is required; the first build or invalid baseline emits no candidates. Matching IDs are compared without `collectedAt` or URL-check `health`. Changes/removals propagate transitively only through explicit `references`/`based_on` edges, where source depends on target. Current and prior dependency edges retain deletion impact; cycles are bounded. `explains`, `related`, and `uses_with` never establish a dependency. Candidates describe changes since the previous publication, so another unchanged build clears them; they are not a persistent review inbox and do not automatically change publication status. New items without a matching baseline ID are not classified as changed. Generated timestamps do not trigger candidates.

`report.json` records source-master counts separately from `public_counts`; the former must not be read as the number of published nodes.
